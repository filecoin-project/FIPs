# FIP-0121: Remove the Fil+ Actors (f06, f07, f080)

## Simple Summary

[FIP-0118](./fip-0118.md) (Solstice) froze the verified registry (f06), DataCap (f07) and root key holder (f080) actors and said a later upgrade would delete them. This is that upgrade. The three actors and their state leave the state tree; their balances are burned; the `verifiedregistry` and `datacap` actor types leave the bundle.

## Abstract

Since network version 29 every write method on f06 and f07 rejects, the miner and market actors never call them, and f080 exists only to be f06's root key. None of the remaining actors read their state. It is nevertheless still included in every state root, every snapshot and every node's hot blockstore, and every node implementation still ships code to decode and invariant-check it.

At the activation epoch of a network upgrade including this FIP, the state migration removes the three actors from the state tree, sends their balances to the burnt funds actor (f099) and installs an actor bundle without the `verifiedregistry` and `datacap` types. The historical record stays reachable at any pre-activation state root. Apart from the multisig receiver hook, actor methods, parameters and wire formats are unchanged.

## Change Motivation

FIP-0118 Section 1.6 deferred actor removal until no live path touched the actors. That condition held from the activation of nv29. The remaining reasons to act now are weight and maintenance:

- **State and snapshot size.** The frozen claims and allocations tables are included in every snapshot and occupy every node's hot store even though no transaction can ever read them again. Measured on mainnet at epoch 6,501,421 (2026-10-30), counting distinct blocks reachable from each actor's head:

  | Actor | Blocks | Bytes |
  |---|---:|---:|
  | f06 | 13,971,578 | 11.82 GB |
  | f07 | 2,063 | 306 KB |
  | f080 | 2 | 173 B |

  The f06 claims table is 99% of it: 123 million claims across 2,282 provider HAMTs. The claims table compresses to 6.3 GB at zstd-3; the Forest mainnet lite snapshot for the same day is 84.8 GB zstd-compressed, so these actors are roughly 7.5% of a snapshot download. They appear once no matter how many epochs of state the snapshot includes, since the DAG is frozen.

- **Maintenance.** Each implementation carries two actor types, their Go/Rust state mirrors, the claims-against-miners invariant check, and a dozen RPC methods, all of which can only return frozen data.

The removal is deliberately small. There is no new mechanism to design, only a deletion that FIP-0118 already committed to.

## Specification

### Migration

At the upgrade epoch the state migration:

1. Adds the balances of f06, f07 and f080 to the balance of f099. At the time of writing f06 holds 0.00100000666 FIL, f07 holds 0.00000000666 FIL and f080 holds nothing; the rule applies to whatever the balances are at the upgrade epoch.
2. Deletes the actor entries for IDs 6, 7 and 80 from the state tree.
3. Updates the system actor's built-in actor manifest to the new bundle, which no longer includes `verifiedregistry` or `datacap`.

The other actors' state doesn't change. The total of all actor balances is unchanged by the migration.

The migration fails if f06, f07 or f099 is missing, or if the `verifiedregistry` or `datacap` code CID is found at any other address. f080 is deleted whatever its code and is allowed to be missing: it is a multisig on mainnet and the calibration network, but a test network's genesis can make it an account.

### Addresses

IDs 6, 7 and 80 remain unassigned forever. The init actor allocates IDs from 100, so none of them can be reallocated. A message or internal send whose receiver resolves to one of them fails with `SYS_INVALID_RECEIVER` (exit code 5), the same as any other nonexistent ID address.

The init actor's address map is left as it is. Mainnet and calibration network don't have entries for any of the three IDs. Where a test network's genesis made f080 an account, that account's key address still maps to ID 80 after the migration. A send to the key address resolves through that entry to ID 80, doesn't find an actor there, and fails with `SYS_INVALID_RECEIVER`, just like a send to f080 itself. Without the entry the FVM would instead create a fresh account for the key.

The [FIP-0057](./fip-0057.md) set of preloaded actors (0 to 7, 10 and 99) is also left as it is: a message that looks up ID 6 or 7 is still not charged `p_actor_lookup` for it, although the lookup now misses. Changing the set means a new gas price list, which can wait for the next upgrade that needs one.

### Actor bundle

The `verifiedregistry` and `datacap` actor types are removed from the built-in actor bundle. The multisig type is unaffected; f080 was an ordinary multisig instance.

The FVM numbers built-in actor types by their position in the bundle manifest, starting at 1, so a manifest cannot skip a number. Removing two entries therefore moves `placeholder`, `evm`, `eam` and `ethaccount` from 13, 14, 15 and 16 to 11, 12, 13 and 14. Actor code gets a type number from the `get_builtin_actor_type` syscall and compares it against an enum compiled into the same bundle. The number doesn't appear in any state, message or event, and the EVM doesn't have a precompile that would return it (a `get_actor_type` precompile was removed before FEVM launched, and it returned a coarse category rather than the number), so the renumbering is contained in the bundle.

### Multisig receiver hook

The multisig actor's `UniversalReceiverHook` method (FRC-42 number of `Receive`) is removed. [FIP-0050](./fip-0050.md) added it so a multisig could receive DataCap, the only FRC-0046 token the network has had. A call to that method number now reaches the multisig's fallback, which accepts any exported method, so the one observable difference is that malformed parameters are accepted instead of rejected. [FIP-0055](./fip-0055.md) made the same change to the account actors.

### Genesis

A genesis state for the activation network version or later contains none of the three actors. Genesis templates stop requiring a verified registry root key.

### Unchanged

Everything FIP-0118 left serialised but inert stays: `verified_allocation_key` on piece manifests, claim declarations in `ExtendSectorExpiration2` and `DealProposal.verified_deal` are still accepted and still ignored. `GetDealVerified` still returns the stored flag. Sector `verified_deal_weight` is untouched. Apart from the multisig hook above, the FRC-42 method numbers and exit codes of every remaining actor are unchanged.

## Design Rationale

**Burn the balances.** The FIL in f06 and f07 arrived by plain value sends to actors that have no method that could spend it, about a thousandth of a FIL in total. The protocol's circulating supply subtracts the balance of f099, so it falls by that amount. f080 has no balance; if it acquires one before activation it is burned under the same rule rather than special-cased.

**Remove f080 as well.** It was created at genesis to hold f06's root key and has never had another purpose. It is the only key-owned actor this FIP touches (f06 and f07 are the protocol cleaning up after itself, f080 is a multisig with signers). The only call it could ever usefully make now rejects, and it sits at a reserved ID that appears as protocol infrastructure.

**Renumber the actor types.** Keeping `placeholder`, `evm`, `eam` and `ethaccount` at 13 to 16 would take either two dummy entries in every future bundle (the FVM compiles every manifest entry, so each needs its own valid WASM module) or a new manifest format that carries explicit numbers, which is an FVM change. Renumbering is a four-line change to an enum that the builtin-actors build already checks against the manifest.

**A suggestion for actors-utils.** The DataCap actor was the only FRC-0046 token on the network, and its receiver hooks were the only use of `fvm_actor_utils` in builtin-actors. User-deployed actors are EVM contracts, so the Rust token reference libraries in actors-utils (`frc46_token`, `frc53_nft`, `fvm_actor_utils` and their test actors) are left with historical state decoders as their only consumer, and those pin released versions. Every remaining consumer, builtin-actors and Forest's state crates alike, uses the same FRC-0042 `method_hash!` macro and little else, therefore it seems appropriate to archive the repository once that macro is published from ref-fvm. That is a cleanup for maintainers to weigh, not something this FIP requires.

## Backwards Compatibility

The on-chain record of Fil+ (verifiers, allocations, claims, DataCap balances and allowances, the root key multisig) is reachable only at state roots before activation after this upgrade. Archival nodes and pre-activation snapshots will continue to include it. Anyone who wants the final state of Fil+ in a convenient form should export it before activation; the data does not change between now and then.

Node RPC methods that read these actors (in Lotus: the `StateGetAllocation*`, `StateGetClaim*`, `StateVerifierStatus`, `StateVerifiedClientStatus` and `StateVerifiedRegistryRootKey` families) return an actor-not-found error when asked about any state after the migration.

Block explorers and indexers that decode state by actor code CID will no longer see actors with the `verifiedregistry` or `datacap` code after activation and must not treat the absence as an error.

## Test Cases

- Migration: an input tree with f06, f07 and f080 at known balances yields an output tree without them, with f099 increased by exactly the sum, every other actor's balance and head unchanged, and the system actor pointing at the new manifest. Run against the mainnet and calibration network state at a recent epoch.
- Migration failures: a tree missing f06, f07 or f099, or holding a second actor with the `verifiedregistry` or `datacap` code, aborts the migration. Trees where f080 is a multisig, is an account or is missing all migrate.
- Post-activation: a message to f06, f07 or f080 fails with `SYS_INVALID_RECEIVER`; the state invariant checker passes without a verified registry or DataCap summary.
- Renumbered types, run under the FVM on a network upgraded through activation and on one whose genesis is at the activation network version: a send to a fresh f410 address creates a placeholder, an Ethereum transaction from it promotes it to an EthAccount, it deploys a contract through the EAM and the contract executes. On the upgraded network a placeholder, an EthAccount and a contract created before activation still work after it.
- Genesis at the activation network version: there is no actor at ID 6, 7 or 80, and the init actor's address map doesn't have an entry for them.
- Bundle: the manifest for the activation actors version doesn't have a `verifiedregistry` or `datacap` entry.

## Security Considerations

Every change is in the migration. After activation the runtime executes today's actor code minus two actor types, recompiled against the renumbered type enum, which shrinks the surface that implementations need to keep correct. The only funds affected are the trivial balances above, which are unspendable before this FIP anyway.

A migration that forgets to reassign a balance would silently reduce the sum of balances in the tree; the migration test must assert conservation. A migration that leaves a stale manifest entry would leave an unreachable code CID in the system actor's table; the test must assert the manifest contents.

If the builtin-actors type enum and the manifest got out of step, actors would mistake each other's types and caller checks would pass or fail wrongly. The builtin-actors build fails on a mismatch, and the renumbered-type test cases run each affected type through the FVM.

## Incentive Considerations

None. Since nv29 the miner actor computes power, pledge and reward from sector state alone. About 140 PiB of minted-but-unallocated DataCap and the ~126 million allocation IDs ever issued become unreadable on chain; they were already unusable.

## Product Considerations

Nodes get a smaller state tree and smaller snapshots, so a faster initial sync and less hot-store churn. Archival nodes keep what they already have. Fil+ tooling that still points at these actors must be retired or pointed at historical state.

## Implementation

- **builtin-actors:** remove the `verifreg` and `datacap` crates from the bundle, the `VerifiedRegistry` and `DataCap` entries from the actor type enum (renumbering the four after them), the singleton address constants, the verifreg policy constants, the verifreg/datacap arms of the state invariant checker, the multisig `UniversalReceiverHook` and with it the `frc46_token` and `fvm_actor_utils` dependencies.
- **go-state-types:** migration for the activation actors version (balance transfer, actor deletion, manifest update; the state tree wrapper gains a delete, since every earlier migration copied or transformed each actor), removal of the two manifest keys from the new version's key list, invariant checker arms removed, multisig method table without `UniversalReceiverHook`.
- **Lotus:** wire the migration in the upgrade schedule; remove the verifreg and DataCap actor adapters for the new version; genesis stops creating the three actors at or after the activation network version; RPC methods return actor-not-found after activation. The `filplus` and `lotus-shed verifreg` commands are already gone.
- **ref-fvm:** a comment on the preloaded actor list marking IDs 6 and 7 for removal in the next price list. The code is unchanged.
- **Forest:** equivalent migration and decoder changes.
- **actors-utils (suggested, not required):** publish the FRC-0042 `method_hash!` macro from ref-fvm, move builtin-actors and Forest onto it, and archive the repository. Forest's other uses are decoders for historical DataCap state (`frc46_token` 15) and `UniversalReceiverHook` parameters (`fvm_actor_utils` 15), both frozen types that can be copied. Published versions stay on crates.io and IPC vendors its copy of `frc42_dispatch`.
